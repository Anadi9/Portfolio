## 2. Data

New Supabase project (see decision D5), Postgres. One migration: `supabase/migrations/20260925000000_kit_packs.sql`. RLS is enabled on every table with **no policies**, so the anon and authenticated roles see nothing; only the server, using the secret key, reads or writes.

```sql
create table stripe_events (
  id          text primary key,              -- evt_…
  type        text not null,
  received_at timestamptz not null default now()
);

create table kit_orders (
  id                    uuid primary key default gen_random_uuid(),
  stripe_session_id     text unique,          -- null only for a free upgrade (credit covered it)
  stripe_payment_intent text unique,          -- pi_…, how charge.refunded finds the order
  email                 text not null check (email = lower(email)),
  amount_total          integer not null check (amount_total >= 0),  -- minor units
  currency              text not null check (currency in ('usd','inr')),
  kind                  text not null check (kind in ('purchase','upgrade')),
  status                text not null default 'paid' check (status in ('paid','refunded')),
  created_at            timestamptz not null default now(),
  refunded_at           timestamptz
);
create index kit_orders_email_idx on kit_orders (email);

create table kit_order_items (
  order_id uuid not null references kit_orders (id) on delete cascade,
  pack_id  text not null check (pack_id in ('full','data-security','auth','launch','ai-discipline','lovable-bolt')),
  amount   integer not null check (amount >= 0),   -- what was paid for this line, after discounts
  unique (order_id, pack_id)
);
create index kit_order_items_pack_idx on kit_order_items (pack_id);
-- order_id is covered by the unique index (leading column).

create table kit_access (
  email      text primary key check (email = lower(email)),  -- "email unique"
  token_hash text not null unique,
  token_salt text not null,
  created_at timestamptz not null default now()
);


alter table stripe_events   enable row level security;
alter table kit_orders      enable row level security;
alter table kit_order_items enable row level security;
alter table kit_access      enable row level security;
```

Additions to the columns you listed, and why:
- `kit_orders.stripe_payment_intent`: `charge.refunded` carries the charge and its PaymentIntent, not the Checkout Session. Without it the refund can't find its order.
- `kit_access.token_salt`: the thanks page must show *the same link that was emailed*, but only a hash is stored. So the token is `HMAC-SHA256(KIT_TOKEN_SECRET, salt)`, and the table keeps the salt and `sha256(token)`. A database leak alone gives no working link (the secret lives only in Vercel env), and the server can re-create the link for someone holding a paid session id. Rotating a buyer's link = new salt.
- Rate limiting reuses `createRateLimiter` and `clientIp` from `src/lib/scan/rate-limit.ts` (in memory, per function instance, as `/api/scan` does). It stops one visitor or script hammering an endpoint; it isn't a defence against a distributed attacker, and doesn't need a table. The 60-second signed URLs and the ownership check are what protect the files.

"Owns a pack" = a `kit_order_items` row for that pack whose order has `status = 'paid'`, joined by `email`. Owning `full` means owning everything.

Release catalog (no table): `src/data/kit/releases/1.2.0.json` is a copy of the manifest; `src/data/kit/index.ts` exports all releases, newest first, and `LATEST`. A new release = drop in the new manifest and upload its zips. Storage path: `kit/<version>/<zip>`, e.g. `kit/1.2.0/production-kit-auth-v1.2.0.zip`, in a private bucket named `products`. Old versions stay.

## 3. What runs on the server

All new routes are one function, `api/kit/[action].ts`, dispatching to `src/lib/kit/handlers.ts` (one function instead of seven, in case the plan caps functions per deployment). Logic lives in `src/lib/kit/*` so Vitest can reach it. The dev plugin's path regex is widened to allow one sub-folder (`/api/kit/checkout` → `api/kit/checkout.ts`).

| Route | Input (validated with zod) | Does |
| --- | --- | --- |
| `GET /api/kit/prices` | none | Looks up the six Prices by lookup key (`GET /v1/prices?lookup_keys[]=…&expand[]=data.currency_options`), returns `{ usd: { full: 1900, … }, inr: { … } }`. `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400`. Display only. |
| `POST /api/kit/checkout` | `{ packIds: string[] }`, max 12, each in the manifest | Rate limit 10/min per IP. Dedupe; any `full` → `["full"]`; empty or unknown → 400 with the offending id. Creates a session: `mode=payment`, one line item per pack, `currency` from the visitor's country (INR for India, else USD), `allow_promotion_codes`, `billing_address_collection=required` (Stripe India needs name and address on export sales), `metadata[pack_ids]`, `metadata[kit_version]`, `success_url=/kit/thanks?session_id={CHECKOUT_SESSION_ID}`, `cancel_url=/products/production-kit?packs=…#picker`. Returns `{ url }`. |
| `POST /api/stripe-webhook` (extended, same URL) | raw body + signature | See section 5. |
| `GET /api/kit/order?session_id=cs_…` | session id regex (existing `isSessionId`) | Thanks page data. Retrieves the session from Stripe. Unknown → 404, unpaid → `{ status: 'unpaid' }`. Paid but no order row yet → `{ status: 'pending' }`. Paid with order → `{ status: 'ready', packs, link, upgrade }` where `link` is the re-derived `/kit/downloads/<token>`. |
| `GET /api/kit/library?token=…` | token regex (43 chars base64url) | Rate limit per token. Looks up the email by `token_hash`, returns owned packs (non-refunded), each with every release version, newest first, and the upgrade offer. Unknown token → 404. |
| `GET /api/kit/download?token=…&pack=…&version=…` | token, pack id, version in catalog | Rate limit 30/hour per token. Re-checks ownership (owning `full` counts only for `full`; the page only shows `full`). Creates a Supabase signed URL, 60 s, with `download: <zip name>`, and 302s to it. |
| `POST /api/kit/upgrade` | `{ token }` | See section 7. |
| `GET /api/production-kit-download?session_id=…` | unchanged | Earlier buyers' links. Not touched. |
| `POST /api/production-kit-checkout` | unchanged until step 9 | Removed from the page in step 5; the file stays until you confirm nothing calls it (step 9 turns it into a 410). |

Server-only env vars (Vercel, never `VITE_`): `SUPABASE_URL`, `SUPABASE_SECRET_KEY` (`sb_secret_…`), `KIT_TOKEN_SECRET` (32 random bytes). Supabase is reached with `@supabase/supabase-js` (one new dependency; the storage signing and conflict codes aren't worth hand-rolling). Stripe stays on plain `fetch`, matching `stripe.ts`.

Prices on the page: `scripts/fetch-kit-prices.mjs` runs before `vite-react-ssg build`, writes `src/generated/kit-prices.json`, so the prerendered HTML and the JSON-LD carry Stripe's prices. After hydration the page refreshes from `/api/kit/prices`. If the build can't reach Stripe: on `VERCEL_ENV=production` the build fails (never ship guessed prices); anywhere else it writes the manifest's suggested prices with `source: "manifest"`, and the page shows a small "Dev: suggested prices, not from Stripe" note.

## 5. Webhook fulfilment (`api/stripe-webhook.ts`, same URL)

Following the kit's template (`templates/next/app/api/stripe/webhook/route.ts`), adapted to plain `fetch` and the existing `verifyStripeSignature`:

1. Raw body, verify signature → 400 on failure (unchanged).
2. `insert into stripe_events` first. Unique violation (`23505`) → 200, nothing done. Other DB error → 500.
3. Handle; on any throw, delete the event row and return 500 so Stripe retries.

Events:
- `checkout.session.completed` with `payment_status` `paid` (and `no_payment_required`, D8), and `checkout.session.async_payment_succeeded`:
  - `GET /v1/checkout/sessions/{id}/line_items?expand[]=data.price`. Map `price.lookup_key` → pack id. Unknown lookup key → throw (retry, and I see it in logs).
  - Upgrade session (`metadata.upgrade = "true"`) → one item `full`, `kind = 'upgrade'`, email from `metadata.email` (not from what they typed in Checkout).
  - Legacy session (`metadata.product = "production-kit"`, created by the old checkout before the switch) → one item `full`, and the new delivery email with a downloads link, so a checkout opened just before the deploy still delivers. The old `/products/production-kit/thanks` page it returns to still shows the old download link, which still works.
  - Insert order (on conflict `stripe_session_id` do nothing) and items; get or create `kit_access` for the email; send the email via Resend with idempotency key `kit-delivery/<session id>`: pack names, the `/kit/downloads/<token>` link, where to start, upgrade line if no full. Sale notice to you as today.
- `checkout.session.completed` with `unpaid` → nothing (async payment still settling).
- `charge.refunded`: find the order by `payment_intent`. Full refund (`amount_refunded === amount`) → `status = 'refunded'`, `refunded_at = now()`. Partial refund → no change, email you a notice. No order found (a legacy sale) → 200, logged.

Stripe endpoint events to add: `charge.refunded`. The `stripe:listen` script gets it too.

## 7. Upgrade to the full kit

`POST /api/kit/upgrade { token }`, rate limited 5/min per token:
1. Token → email. Already owns full → 409 "You already have everything."
2. Currency: the currency of their paid pack orders (if mixed, the visitor's checkout currency, counting only orders in it).
3. `credit = sum(kit_order_items.amount)` over their `paid` purchase orders in that currency (what they actually paid, after promo codes).
4. `due = fullPrice(currency) − credit`, full price from Stripe (`kit_full`).
5. `due <= 0`, or below Stripe's minimum charge ($0.50 / ₹ equivalent) → insert an `upgrade` order with `amount_total = 0`, item `full`, return `{ granted: true }`; the page reloads the library.
6. Else create a Checkout Session with `price_data { currency, unit_amount: due, product: <kit_full's product id> }`, `customer_email: email`, `metadata { upgrade: "true", email }`, success/cancel back to `/kit/downloads/<token>`. Return `{ url }`. Webhook grants full.

The amount is computed here every time; the browser only sends the token. The "Upgrade to everything for $X" label on thanks, downloads and the email uses the same function.

### D7: the free check and the funnel

What `/scan` can find: tables the public key can read (critical) and public storage buckets (warning). Both are exactly what **Lock Down Your Data** fixes. `/teardown` scores AI products on defensibility and evals; none of the packs answers its findings, and its visitors are a different audience.

1. **Kit page hero**: the main button goes to the picker. Under it, one plain line: "Not sure what's wrong? Run the free Supabase check. It takes 30 seconds." → `/scan`. Most visitors diagnose themselves faster from the pain cards, so the check is the fallback for anyone who can't tell, not a detour.
2. **Pain cards are the diagnosis.** Each card's headline is the pack's `problem` ("Can strangers read or change my database?"). Clicking "Get this pack" sets `?pack=<id>` and scrolls to the picker with that pack ticked.
3. **`/scan` with findings**: the existing "Rather close them yourself?" line changes from "The $19 Production Kit" to "Lock Down Your Data ($9) has the RLS audit and the attack tests I use." → `/products/production-kit?pack=data-security#picker`. A specific $9 fix for the problem they just saw is an easier yes than a $19 bundle, and the nudge offers the full kit once they're in the picker. The free audit stays the main CTA there, as now.
4. **`/scan` with a clean result**: the "What this doesn't cover" panel already names auth, deploys and performance. Add: "The Production Kit has a pack for each." → `/products/production-kit#picker` (nothing preselected).
5. **Analytics**: `scan_kit_click` gains a `pack` property so you can see how many kit visits start from a finding.

Later, outside this job: the fix notes' `FixCta` could preselect the pack for each note's topic (an auth note → `?pack=auth`).

## 12. Edge cases

- Checkout opened on the old page, paid after the deploy → legacy branch in the webhook (section 5).
- Same email buys twice → one `kit_access` row, one link; the second email repeats the same link.
- Buyer types a different email in the upgrade checkout → ignored; `metadata.email` decides.
- Buying a pack they already own (or a pack while owning full) → allowed by Stripe; the picker on the downloads page doesn't offer it, but the product page can't know who you are. Accept it; you can refund. (No account system; this is the trade.)
- Webhook arrives before the thanks page polls → ready at once; after → pending then ready.
- Webhook fails after inserting the order but before the email → event row deleted, Stripe retries, order insert is a no-op, the email's idempotency key stops a duplicate.
- Partial refund → notice to you, no change in access.
- Price missing in Stripe (lookup key typo) → checkout 500 with "checkout not configured" logged; the prices API omits that pack, and the picker shows it as "Not available" rather than a guessed price.
- `?packs=` with junk → junk dropped; `?packs=full,auth` → full only.
- Supabase paused/down → checkout still works (it doesn't touch the DB), the webhook 500s and Stripe retries for up to 3 days; downloads show the error state.
- Signed URL shared → expires in 60 s.
- Token leaked → you can rotate it by changing the salt (a one-line SQL I'll include in the runbook).
- JS disabled → the prerendered page still shows every pack, price and file list; checkout needs JS (as today).
